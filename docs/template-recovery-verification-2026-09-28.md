# Saved-look recovery, local verification

The installed 1098 development app showed an existing custom look, **Editorial Index**, in the local `visual-demo` workspace. The long-running development server began rejecting the saved look's `showCaptions` property and returned 500 for the whole workspace pool. The current source accepts that property, and a fresh process validated the stored definition. A stale development module is plausible, but the cause has not been confirmed by restarting the server. Next.js 16.3.4 documents separate `.next/dev` output and permits concurrent `next dev` and `next build`; the earlier suspected build-directory collision is not supported by that documentation.

In the isolated `Folder view proof 2026-09-28` fixture, a note appeared under **Unsaved items** with a retry action. A direct read from local Postgres confirmed the exact note title and body were already saved once. The capture flow now reads the exact saved item after a failed broad pool refresh, so an unrelated look failure need not mislabel a confirmed save. The read checks item access and is keyed to the create receipt's ID. Three action tests cover an allowed exact read, denied access, and a signed-out caller. This new fallback has not yet been triggered in a native failure run.

The store now treats an unreadable saved look version as presentation failure: the picker/library use the latest valid version, exact look lookup returns null, and a pinned item falls back to its basic built-in view. The document content and exact pinned reference are not rewritten. A bounded warning names the look version without logging its definition or private content. Local database tests covered an invalid latest version, valid predecessor, exact and pinned lookup, and library history; a pool test covered fallback rendering. Eight focused tests, TypeScript, and touched ESLint passed (two existing store warnings).

The running development app later recovered without a service restart. In the installed 1098 app the recovery card disappeared, the folder showed one **Editorial proof note**, and a fresh local Postgres read confirmed exactly one matching item (ID `87b9fd02-4b19-48a1-86b4-d2315672ff43`). The source of the earlier stale schema rejection remains unconfirmed. The app's **View** dropdown was a personal display choice; assigning **Editorial Index** through **Choose default type → Use this look** saved its existing version 1 as the folder default. A fresh store read confirmed that reference. The native readback demonstrates recovery and no duplicate, but does not isolate whether the new exact-read fallback or the development server's own refresh reconciled the earlier card.
