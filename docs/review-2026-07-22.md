# TextText unified document implementation review

Updated 2026-07-23. This replaces the pre-build baseline review. The unified
document architecture is implemented in the current working unit and the
remaining statements here are release risks, not an unstarted backlog.

## Verdict

The old architecture had separate render and edit paths for articles, projects,
talks, notes, and bookmarks. That was the wrong boundary. The rebuild now has:

- One strict `DocumentSnapshot`
- One closed presentation grammar
- One renderer for app, public URL, previews, and export
- One Yjs document model for collaborative content
- One structured `.textpack` projection with Markdown compatibility
- One shared AI, UI, and MCP command surface
- Explicit fail-closed visibility independent of presentation

The old readers, editor preview route, and bespoke body editor stack are removed.

## Evidence by boundary

### Content and files

- `src/lib/documents/model.ts` defines the canonical content and presentation
  snapshot.
- `src/lib/documents/sync.ts` defines deterministic structured sync and the rule
  for external Markdown edits.
- `mac/Sources/TextTextFileProviderKit/TextBundlePackage.swift` materializes
  `document.json` and package-local assets.
- `src/app/api/sync/v1/files` negotiates structured or legacy Markdown
  representations without breaking old clients.

Risk addressed: a Markdown-only write no longer erases presentation or assets.
Unknown frontmatter cannot become render input.

### Render safety

- `src/lib/presentation/schema.ts` is strict and closed.
- `src/lib/presentation/templates.ts` validates every built-in through that same
  schema.
- `src/components/document/DocumentRenderer.tsx` is the only interactive render
  compiler.
- `src/lib/presentation/export.server.tsx` uses the same renderer and CSS.

Risk addressed: AI and imported templates cannot inject HTML, CSS, scripts,
event handlers, or arbitrary components.

### AI authoring

- `src/lib/presentation/operations.ts` provides bounded, validated mutations.
- `src/lib/ai/tools.ts` defines list, customize, and apply-template tools.
- `src/lib/mcp/tools.ts` executes those tools through audited `store.ts`
  operations.
- `src/components/document/TemplateGallery.tsx` previews actual engine output.

Risk addressed: a small model edits a valid artifact incrementally instead of
having to generate a perfect page in one response.

### Template storage and versioning

- Built-ins are immutable code artifacts under the reserved `texttext.` prefix.
- Workspace templates are immutable versions in `document_templates`.
- A document pins an exact `{id, version}`.
- A folder has an exact default template reference for new documents.

Risk addressed: editing a shared look cannot silently restyle already published
documents. Concurrent template work produces new versions rather than overwrites.

### Privacy and access

- `posts.visibility` defaults to `private`.
- `src/lib/documents/visibility.ts` forces notes and bookmarks private.
- Public queries require explicit `public`; link reachability requires explicit
  `link`.
- Named roles and team access remain below the UI and tool layers.
- Guest capability links provide revocable viewer, commenter, or editor access.

Risk addressed: an unknown template id or capability list cannot publish a
document. Presentation is not an authorization input.

### Collaboration

- `src/lib/collab/document.ts` maps the full document to Yjs.
- `src/lib/collab/provider.ts` persists an IndexedDB outbox, fences generations,
  retries transient failures, and carries awareness.
- Collab routes use the same effective item access resolver as ordinary reads.
- Materialization writes the canonical document, not only a body string.

Risk addressed: local edits no longer wait for server acknowledgement and remote
refreshes do not own active editor state. Owner, account editor, and guest editor
sessions share one merge model.

## Adversarial findings retained as invariants

1. Capabilities are not permissions. A template may declare collaboration or
   publish controls, but the permission resolver decides whether a caller may
   use them.
2. Presentation cannot determine containment. Folder membership is authoritative.
3. Presentation cannot determine privacy. Explicit visibility is authoritative.
4. `text.md` cannot encode the whole product. It is an editable projection;
   `document.json` preserves structure and presentation.
5. `document.json` cannot hide executable behavior. It validates as data only.
6. Type definitions do not use Yjs. Immutable coarse versions are simpler and
   prevent partially valid shared specs.
7. P2P does not solve durability, permissions, offline delivery, or publish.
   The server-mediated baseline remains the foundation.
8. File Provider cannot be the live editor database. It is a durable projection
   with a different latency and coordination model.

## Release gates

- The additive migration runs idempotently, converts every live and trashed row,
  and then enforces a non-null canonical snapshot with a validated database
  constraint.
- The canonical audit validates every snapshot and verifies that its search
  projections match.
- Structured and legacy sync clients select the correct hash and representation.
- A `.textpack` with `document.json` and assets round-trips through the native
  provider.
- Notes and bookmarks remain private after migration and publication attempts.
- Existing public article, gallery, and talk URLs retain their audience.
- Two Yjs editors preserve independent title and body edits plus presentation.
- Guest editor, commenter, and viewer links resolve only their granted role and
  can be revoked.
- Built-ins, database templates, AI operations, and imported templates all pass
  the same validator.
- App, public route, preview, and export compile through the same renderer.

`npm run verify:release` is the only full gate. The document-engine evaluation
the canonical storage audit, and the native document projection self-test are
part of that gate and the app-owned health report.

## Deliberate deferrals

The first version does not need:

- Arbitrary user HTML, CSS, or JavaScript
- P2P transport
- Full website generation
- Pixel-perfect cloning
- Collaborative character editing of template definitions
- Mandatory cloud AI

These are not missing architecture. They are excluded scope. Any future proposal
must show a measured product need and preserve the strict engine boundary.

## Smallest proof slice

The architecture is proven when one existing Markdown article can be migrated to
a structured document, switched to another built-in or workspace template,
edited concurrently by an owner and guest editor, rendered through the same
engine in app and at a link, exported, and materialized as a `.textpack` that
still opens in an old Markdown-only client.

The current implementation covers that slice. Release verification must prove it
as one coherent source state before shipping.
