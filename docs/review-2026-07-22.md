# Texttext deep review + body of work (2026-07-22)

A code-grounded review of three subsystems, with what works / half-built /
missing and an ordered "to finish it" for each. Produced by a multi-agent pass
(6 readers + 3 adversarial verifiers + 3 synthesizers) reading the actual code.
This is the backlog we work from.

Recurring theme: the internal docs drift from the code in BOTH directions. MCP
and collab are more finished than the notes claim; "AI-defined types" is less
built than the "AI generates specs" line implies. Trust the code.

## Headline verdicts

- **AI** - MCP is production-grade and externally connectable today; bring-your-own
  Claude/GPT keys work but are unreachable on the Mac (cloud only fires as a
  fallback; no override, no model picker).
- **Collaboration** - real Yjs CRDT, robust for its scope, no silent lost updates,
  but collaborator-to-collaborator only (the OWNER is excluded from the shared
  doc), no live cursors, and the invite has no accept step.
- **Custom item types** - essentially at zero. The vision dies at the first wall
  (frontmatter allowlist rejects unknown fields; the type enum is fixed). The gap
  is narrow but real: storage + one policy flip + an authoring surface.

## Cross-cutting priority

Highest-leverage, lowest-risk first:
1. **"Use my cloud key" override in the assistant sidebar** - makes Claude/GPT
   actually usable on the Mac (one UI change; the capability is already built).
2. **Make the owner a first-class co-editor** - turns collab from an invited-only
   niche into real multiplayer.
3. **Custom types steps 1-3** (frontmatter policy + `posts.metadata` + a
   `custom_types` table) - the biggest feature, the biggest build; steps 1-3 are
   a clean self-contained unit.

## AI integration

Three AI surfaces route through one executor (`runWorkspaceToolForSession`): the
MCP server for external agents, the on-device Apple assistant, and a
bring-your-own cloud-key path. The "one command surface, three consumers" claim
is real and verified, so privacy, audit, and scope invariants hold no matter
which model is calling.

### What works

- **External agents connect first-try in production.** `https://texttext.app/api/mcp`
  is a real Streamable-HTTP MCP endpoint with a complete, standards-correct
  discovery chain: RFC 9728 protected-resource metadata (plain and suffix forms),
  RFC 8414 auth-server metadata, RFC 7591 dynamic client registration, PKCE S256,
  and a Notion-style zero-config `/.well-known/mcp.json`. Claude Desktop/Code,
  Cursor, VS Code, and Codex all have copy-paste recipes in `/docs/ai`. Auth order
  is correct (`withMcpAuth` authenticates before the scope gate; no read-before-set
  race). The whole loop is a codified release gate (`scripts/test-oauth-mcp-loop.py`).
- **26 real workspace tools** (8 read, 18 write). The executor switch is exhaustive;
  every case is implemented. Tags and `[[wikilinks]]` are surfaced (outbound links
  resolved + backlinks on `read_item`), deletes are soft (Trash) with no
  permanent-delete tool, hash + revision give dual conflict control, every mutation
  writes an `action_audit` row.
- **OAuth tokens are the sync `wsk_` tokens**, scoped to `read` or `sync`, minted with
  1h expiry and `wrt_` refresh rotation with replay-detection family revocation. The
  token owner's owned blog is the workspace, so no tool can cross tenants.
- **Bring-your-own cloud keys work end-to-end.** A real, owner-gated Settings UI lets
  the user paste an Anthropic or OpenAI key (provider `<select>` + password field +
  Add/Replace/Remove). Keys are AES-256-GCM encrypted at rest, read server-side only,
  never logged, never returned to the client. `POST /api/ai` builds the provider SDK
  and calls `generateText` with the same workspace tools. On plain web (no native
  bridge) a configured key is the sole assistant path and it fires correctly.
- **The Anthropic model ID is live** (`claude-sonnet-5`), not a placeholder.
- **On-device Apple FoundationModels rung works inside the Mac app**: 8 text ops plus
  Vision OCR plus agentic tool-calling, parity-checked against the Zod tool source,
  free/private/offline, the correct default.

### Half-built / scaffolded

- **`list_access` read/scope contradiction (the one real MCP behavioral defect).**
  Declared `mutability:"read"` (so `/docs/ai` lists it as callable by any assistant
  and the HTTP scope gate lets a read-token request through) but carries
  `requiredScope:"sync"`, so the executor then rejects it. Asymmetric error shape
  (write tools 403 at the gate; `list_access` returns a tool-result error). Fix: gate
  it at the same layer, or document it sync-only.
- **BYO cloud is unreachable from the sidebar on a healthy Mac.** The assistant tries
  native first and only falls to cloud when native is unavailable or hits an asset
  error. There is no "use my Claude key" toggle and no way to force cloud. A Mac owner
  who pastes a key gets nothing from it while Apple Intelligence works. Fully built,
  but architecturally can only ever fire as a fallback.
- **Cloud is non-streaming.** `/api/ai` returns the final reply text only.
- **Cloud tool set is intentionally narrowed** to tools with `confirmation:"none"` and
  no `openWorldHint`, pending a web-path confirmation flow (read + safe writes; no
  delete/publish/restore/sharing/asset-fetch/recapture). Native and MCP get the full 26.
- **Rate limiting is a per-instance in-memory backstop** (20/60s), not a real quota.
- **`serverInfo.name` is still `"write"`** (`handler.ts:19`) while discovery docs brand
  "Texttext"; cosmetic.
- **On-device multi-item reliability** is a soft spot (small model stops after the first
  item; mitigated by decomposition + dedupe; tracked as task #114).
- **Skills** are still localStorage + a 3-item builtin catalog.

### Missing

- Any provider beyond Anthropic and OpenAI (no Gemini, no Ollama/local, no custom base URL).
- Any model picker / per-request model selection (one hardcoded model per provider:
  `claude-sonnet-5`, `gpt-5.5`; user chooses only the provider).
- Image understanding (`altText`/`describeImage` throw, awaiting macOS 27 SDK).
- Streaming cloud responses.

### Bottom line

The MCP server is genuinely production-grade and externally connectable today; the only
true defect in its 26-tool surface is the `list_access` scope mislabel, the rest is doc
drift. The BYO cloud rung is fully built and correct, but invisible on the primary
platform: a Mac owner with Apple Intelligence healthy can paste a Claude or GPT key and
never reach it. Both surfaces are closer to finished than the stale internal docs suggest.

### To finish it

1. Fix `list_access` scope handling (gate at the HTTP layer, or change `mutability` +
   docs). Smallest correct MCP fix.
2. Add a "use my cloud key" override in the sidebar so a configured key is reachable on a
   healthy Mac, not only as a fallback. The single change that makes "run on Claude/GPT"
   usable on the primary platform.
3. Add a model picker (at least a per-provider model field), and confirm `gpt-5.5`
   resolves against the current OpenAI catalog.
4. Set `serverInfo.name` to "Texttext" (`handler.ts:19`).
5. Correct stale tool counts (`CLAUDE.md` "7 tools", `HANDOFF.md` "31-tool" -> 26).
6. (Larger follow-on) Ship the web-path confirmation flow so the cloud tool set widens to
   the full surface, and add streaming to `/api/ai`.

## Collaboration

Sharing, multi-user editing, conflict resolution, durability.

**Is it a CRDT?** Yes. Real-time co-editing is genuine Yjs. Each co-edited post has one
in-memory `Y.Doc` (`BodyEditor.tsx:244-247`) bound to TipTap via
`@tiptap/extension-collaboration`, with Yjs owning undo/redo and standard commutative
convergence. Transport is not `y-websocket`: it is a bespoke HTTP long-poll relay over an
append log (`collab_updates`, monotonic `bigserial seq`); the server is a dumb relay that
stores opaque base64 updates. There is no server-authoritative document.

**Can you add people, and can they edit?** Yes to both, narrowly. You add a collaborator by
email only (no username lookup, no share link, no anyone-with-link). The owner opens
ShareDialog, types an email, picks `editor`, and `shareScopeAction` upserts a
`collaborators` row + audit row. An invited item-editor really edits the body (title, body,
cover, coverCaption, coverHeight, tags) but not `type/slug/status/pinned/starred/folderId/
date` (cannot publish/unpublish, move, rename slug, pin, or delete). Sharing coexists with
"unlisted forever": notes/bookmarks never enter public feeds but remain individually
shareable to named people.

### What works

- Real Yjs CRDT co-editing among invited collaborators, with epoch/generation fencing:
  every append lands only if `clientEpoch = current epoch` in one atomic SQL statement
  (`collab.ts:105-111`); a client that sees a new epoch drops queued edits and remounts.
- Log compaction bounds an active post's log (snapshot past 200 rows via `Y.mergeUpdates`).
- Two mutually exclusive write paths gated by role: the live Y.Doc (collaborator) vs the
  raw-overwrite path (owner pool-shell, sync PUT, MCP, App Intents), which is refused while
  co-editors are present.
- Revision-CAS backstop under the presence gate: `hasActiveCoEditors` is check-then-write
  flipping at the 15s presence-expiry boundary, and every body write also carries
  `expectedRevision` and compare-and-swaps on `posts.revision` (`store.ts:3533-3560`), so a
  write slipping past the presence gate still cannot silently clobber a newer revision - it
  gets a retryable conflict (412 sync / conflict MCP / error pill editor).
- Scoped permission system (workspace/folder/item) with per-request resolution and
  server-side enforcement on every write path; folder shares cascade; private-type carve-outs
  enforced through `resolveItemAccess`.
- Corruption tolerance: undecodable rows skipped while `lastSeq` advances; server rejects
  undecodable/oversized (>512KB) updates on ingest.
- Two pagehide beacons (Yjs deltas + canonical body to `/materialize`) + opportunistic
  presence sweeping.

### Half-built / scaffolded

- No accept/binding step in the invite lifecycle. `collaborators.userId` is written only at
  insert and only if an `email:<addr>` account already existed; nothing sets it on later
  sign-in. Access rides on a live email match. An invitee signing in with a different address
  (Apple private-relay, an alias, a second account) gets zero access with no reconciliation.
- The "accepted" indicator is misleading (`accepted = Boolean(row.userId)` = "had an
  email-provider account when invited," never set for Apple/Google users).
- Invite email fires for item shares only; folder/workspace invites send nothing.
- Presence is a bespoke color-only heartbeat, not Yjs awareness. `y-protocols` is a dep but
  imported nowhere; `collab_presence` has no cursor-position column. UI shows only an avatar
  stack, no live cursors/selections.
- Legacy parallel item-share API (`sharePostAction`) still exists alongside the scoped set.

### Missing

- **The owner is not a first-class co-editor.** Owners and full workspace members route to the
  non-Yjs pool shell (`page.tsx:317-351`, no `collab` prop, no presence). Only a user with
  `canEdit === false` but item-share `canEditContent === true` gets the Yjs collab shell. So
  real-time N-way editing exists only among invited share-collaborators; the owner is a
  presence-guarded external writer who is 409'd while a collaborator is live, and vice-versa.
  The `page.tsx:296-297` comment ("Any signed-in editor joins the same Yjs document") is
  contradicted by routing; code wins.
- No live awareness UI (cursors, selections, typing indicators). Biggest gap vs Notion/Docs.
- No server-authoritative document; reseeding depends on the client replaying the log. No
  headless merge; TipTap schema drift could diverge with no arbiter.
- No workspace-share discoverability (`listSharedWithMe` handles item + folder only; ShareDialog
  defaults workspace invites to `guest`, which grants nothing).
- No offline CRDT persistence (`Y.Doc` in-memory only; the durable offline artifact is a
  separate markdown draft).
- DB-poll transport, not event-driven; a held 25s long-poll pins a serverless instance.

### Durability holes still OPEN

- `collab_updates` row leak (bounded): compaction bounds an active log, but retirement/cleanup
  only fire on a `since=0` editor catch-up (`route.ts:136-141`). A post co-edited once and
  never reopened keeps its compacted log + `collab_state` row until hard delete.
- Tab-death beacon loss (bounded residual, mostly closed): genuine loss needs an over-quota
  (>~64KB) body AND both pagehide beacons dropped AND the post never reopened.

For contrast, holes the tracking docs still flag as open are CLOSED in current code: Hole 1
(live-session external overwrite) via `hasActiveCoEditors` + revision CAS; Hole 2
(between-sessions overwrite) via `retireStaleCollabEpoch` + `materialized_revision` +
epoch-fenced appends + client `onRetired` remount. The "DESIGN ONLY" plan header and the
`collab.ts:442-451` NOTE are stale.

### Bottom line

Real-time multiplayer is real and, for its intended scope, robust: a genuine Yjs CRDT with
external writers refused (never merged-and-lost) while collaborators are live, and a revision
CAS backstop at the one race boundary, so no silent lost update. But it is only partly
production-grade: collaborator-to-collaborator with the owner excluded, no live cursors, an
invite lifecycle with no accept step (mismatched sign-in email silently grants nothing), and
one bounded row leak.

### To finish it

1. Add an accept/binding step that writes `collaborators.userId` on first authenticated access
   by a matching invitee, and reconcile email mismatches (bind any verified session email, or
   invite by account). Closes the private-relay/alias silent failure.
2. Make the owner a first-class Yjs participant (route owners/full members into the same collab
   shell), so all editors live-merge on one doc.
3. Add live awareness UI (cursors/selections) via the already-present `y-protocols` awareness;
   give `collab_presence` a real cursor payload (or move cursors into awareness).
4. Send invite notifications for folder/workspace scopes; surface workspace-scope shares in
   `listSharedWithMe`; change the ShareDialog workspace default off `guest`.
5. Close the `collab_updates` leak with a background sweep / TTL on idle `collab_state`.
6. Move transport to pub/sub / server-authoritative Y.Doc (stop pinning an instance per held
   long-poll; enable headless merge + schema-drift arbitration).
7. Persist the CRDT offline with `y-indexeddb`.
8. Delete the redundant legacy item-share API; fix the stale tracking docs.

## Custom item types

Vision: one text data model, an AI (or user) mints a new document kind with its own fields,
look, and rendering, and it round-trips through save/sync/MCP like any post. Today that is
unbuilt. `post_type` is a fixed Postgres enum (`article/project/talk/note/bookmark`,
`schema.ts:34-40`) with a hardcoded renderer switch duplicated across ~6 files. The one module
that gestures at a spec-driven substrate (`modes.ts`) is dead at runtime.

### What works

- The fixed five-type model end to end (enum + `content.ts` unions + editor allowlists +
  privacy predicates), each behaving correctly.
- Type-to-renderer dispatch for the three renderers (`Reader`/`ProjectReader`/`TalkReader` by
  a ternary; `note`/`bookmark` via default `Reader`, which special-cases bookmark).
- A clean, tested frontmatter round-trip: single-line-per-key, symmetric render
  (`markdown-files.ts:184-221`) and parse (`:316-369`) allowlists, with a well-defined
  `unknownKeys[]` seam computed at every ingest point.
- `validateModeSpec` (`modes.ts:194-226`): a correct, strict, tested "validated data, never
  code" validator (allowlisted keys, pinned `schemaVersion`, fresh-object rebuild).

### Half-built / scaffolded

- `modes.ts` is a real validator with three frozen built-in specs and a test suite, but ZERO
  runtime consumers. Nothing imports `SYSTEM_MODES`/`modeForFolder`/`validateModeSpec` outside
  the module + test; nothing generates a spec, stores one, or renders from one. Its ceiling is
  tiny: pick among 5 fixed view primitives (`timeline|grid|index|single|list`), sort by 4 fixed
  fields, declare item kinds from a closed 7-value list. It rearranges how existing kinds are
  listed; it cannot define a new kind, add a field, or attach rendering (an `onRender` key is
  rejected). A presentation selector, not a schema or render engine.
- The `ItemKind` alias layer (`media_post` <-> `project`, `video_post` <-> `talk`) pretends a
  richer vocabulary exists but maps onto the same five real types.
- `feed_item`/`group_post` (+ the `feeds`/`group` surfaces) are vocabulary-only placeholders
  (no post-type mapping, no DB value, no renderer).
- `action_audit.targetType` includes `"mode"` (`schema.ts:173`) that no code writes.

### Missing

- Any AI or user path that generates a type definition or a `ModeSpec` ("AI generates specs" is
  aspirational).
- Custom fields that persist. Unknown frontmatter keys are hard-rejected by MCP + the in-app
  agent (`Unsupported frontmatter keys`, `tools.ts:820-824` create, `:440-444` update) and
  silently dropped by the sync/File Provider routes (spread only `...parsed.fields`, never
  inspect `unknownKeys`). A custom field survives zero full round-trips.
- Storage for a custom-type definition. No `custom_types`/`type_definitions` table, no general
  `posts.metadata jsonb` bag (the only jsonb columns are strongly typed: `gallery/links/capture`).
  `folders.mode` is normalized to `blog` for anything but `notes`/`bookmarks`.
- A renderer registry (type->component is a hardcoded ternary in ~6 files; a novel `type` falls
  through to default `Reader`).
- Custom rendering per type (no template, no render spec, no CSS hook keyed by type).
- The `info.json` textbundle sidecar is not a viable channel (reconstructed locally, never
  uploaded; decoder is a closed allowlist; `/assets` accepts `image/*` + `video/*` only).

### Bottom line

"AI mints a new document shape" is essentially at zero. A concrete "recipe" type
(`ingredients/time/rating` + custom render) dies at the first wall: the frontmatter allowlist
rejects the unknown keys before anything is stored, and one layer behind it the `post_type`
enum would reject the new type value at the DB. `modes.ts` is the right seed, but nothing
generates specs, nothing stores them, nothing renders from them, and a spec's power stops at
picking a preset view + sort. The gap is real but narrow: missing storage, a policy flip at one
parse seam, and an authoring surface, not an architectural incompatibility.

### To finish it

1. Flip the frontmatter policy from "reject/drop unknown" to "accept keys the active type
   declares." Thread the active type's field schema into `parsePostMarkdownFile` and route
   declared keys into a `metadata` bag instead of `unknownKeys[]` (the single `default` branch,
   `markdown-files.ts:367-368`). MCP reject + sync drop then do the right thing automatically.
   Mirror the emit side in `renderPostMarkdownFile` so declared fields round-trip out.
2. Add a per-post metadata store: `posts.metadata jsonb`, keyed by the type def's field names.
   Thread it through `savePost`'s write set (`store.ts:3501-3523`) and `mapPost`'s read set.
3. Add a home for the type definition: `custom_types { id, workspace_id, slug, name, fields
   jsonb, render_spec jsonb, schema_version }`; validate on write with a `validateTypeDef` in the
   spirit of `validateModeSpec`.
4. Open the `type` enum: replace the `post_type` pgEnum with a text column + soft ref to
   `custom_types.slug`, seeding the five built-ins as rows; turn `POST_TYPE_BY_VOCAB`
   (`markdown-files.ts:281-289`) into a workspace-scoped registry lookup; update editor
   allowlists. The one invasive change + a data migration.
5. Replace the renderer ternary with a registry + render-spec interpreter: one
   `rendererForType(type)` lookup; built-ins register as entries; custom types render from
   `render_spec` as data-driven layout (AI still ships specs, never code).
6. Build the AI authoring surface: a workspace command (shared by UI, in-app agent, MCP) that
   takes a natural-language description, emits a candidate type definition, runs `validateTypeDef`,
   and persists to `custom_types`. Depends on steps 1-5.
