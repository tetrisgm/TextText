# Assistant history status and polling

The owner reported that the Mac assistant repeatedly showed **Syncing** and **Synced**. The status describes assistant conversation history, not document saving. The owner-scoped loop previously performed a clean remote-history read every 30 seconds while the workspace was active, including when the assistant was closed. Each read published both status labels.

The loop now polls for remote history only while the assistant is open and the window is foregrounded. A real local conversation edit still uploads while the panel is closed. Clean reads send an empty upload payload and do not publish **Syncing**; a clean **Synced** state has no visible status or live announcement. Local, offline, and error states retain their status and retry behavior. Creating an empty chat no longer advances the upload revision; migrated messages still do. When the server accepts a sync but cannot retain local approval data, the app keeps **Saved on this device** and waits for a real local edit before attempting that payload again. Remote reads remain available while the rail is open.

Focused verification: 69 tests across conversation sync, assistant hydration, and sidebar UI passed; `npx tsc --noEmit` and touched-file ESLint passed. The sync tests advance a closed panel through 120 seconds and find no timer or remote request, confirm a real edit uploads and reopening refreshes remote history, confirm a fresh empty chat causes no upload, and confirm unretained local approval data is not repeatedly uploaded. The installed 0.202 (1114) app loaded the local source: its document showed **Saved** while its assistant history showed **Saved on this device**. The local server accepted 26 conversation copies, but two local copies included approval data absent from the shared result. After a reload and 35 seconds with the rail open, the warning stayed still without another **Syncing** announcement. Closing the rail removed the status from view. This is live development-source proof, not a new native bundle or public release. At that stage, the assistant still checked remote history every 30 seconds while open and recently active for cross-device updates. The two local-only approvals remained on this device; their server retention was not changed by that status fix.

## Event-driven follow-up

The owner then pointed out that a 30-second full-history read still wastes cloud traffic. The source now makes one read when the assistant first opens, uploads only after local edits, and reads again when the existing workspace change feed reports a different assistant-history version. A quiet open assistant has no recurring history timer. Returning to a foreground tab reads only when its last successful read is at least five minutes old, or when a remote change was deferred while hidden. Transient failures retain bounded retries. Empty history reads no longer create a database row. A real history mutation bumps the shared workspace cursor; quiet cursor requests do not query the assistant-history table, and viewers receive no private history version. The existing compact workspace change feed still long-polls while the workspace is active; this removes the separate full-transcript poll.

Focused verification covers an hour of idle fake time with one read, event-driven replica updates, deferred hidden-tab reads, bounded retries, real-write-only signals, quiet feed requests, and viewer privacy. TypeScript, touched-file ESLint, and focused tests passed. The later [installed follow-up](assistant-sync-acceptance-2026-09-29.md) confirms the quiet history traffic and resolves the two safe approval previews that had remained on this device. The public service has not been updated by these local checks.
